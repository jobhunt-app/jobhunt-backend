# JobHunt App: project plan

## Repos

The product is split across three repos (planned to live together in one GitHub organization):

- **Backend (this repo):** API service, scraper service, database, LLM, speech, evals, infra.
- **Web frontend (separate repo, not created yet):** React + TypeScript + Vite.
- **Mobile (separate repo, later):** React Native.

Milestones below describe the whole product. UI items are built in the frontend repo; in this repo a milestone is done when the API side is done and tested.

## Why

Two goals at once:

1. **A real tool Tigran uses every day:** the job-search script from `~/Documents/job-hunt` rebuilt as a proper web app, with a database, an API, a React UI, and an LLM that does the CV and cover-letter work.
2. **Rehearse the stack of his project starting 1 February 2027:**

> - Develop new features in the Python backend (FastAPI, async) and integrate new voice assistant use cases
> - Integrate LLMs (Azure OpenAI) including prompt engineering, tool calling and RAG/embeddings
> - Implement gRPC streaming and reduce latency along the ASR → LLM → TTS chain
> - Ship containerised services via Azure DevOps pipelines; operate and monitor production (Langfuse, Azure Monitor)
> - Write tests, do code reviews and work in an agile, cross-functional Scrum team
> - Senior: technical ownership of components, architecture input (e.g. multi-LLM, Kubernetes migration), mentoring

It also becomes the portfolio project that closes the gaps interviewers kept probing: production Python, RAG/vector search, LLM evals and observability.

**Out of scope** (other roles on that team): model training or fine-tuning, edge AI, privacy tech, vehicle architectures.

## The product

- **Jobs:** a scraper service pulls from LinkedIn (public search), staff.am, Greenhouse/Lever/Ashby/SmartRecruiters company boards, Himalayas, Jobicy, Remotive, HN Who's Hiring and selected Telegram channels. Jobs are deduplicated, analysed by the LLM (requirements, seniority, location eligibility, US hours, red flags) and scored against the active profile.
- **Tracker:** every job has a status (new, saved, applied, interview, rejected, not relevant, expired), notes and a history. A kanban view plus a filterable table, replacing the browser-only marks of the old page.
- **CV studio:** the master CV as structured data; tailored versions per job, generated by the LLM under strict "reorder, rephrase, trim, never invent" rules **enforced by validation**; rendered to PDF in the original design.
- **Cover letters:** generated and streamed to the UI, editable, saved per job.
- **Assistant:** a chat that uses tools: "find remote AI roles open to Armenia posted this week", "tailor my CV for the Playrix job", "mark Sensor Tower as rejected", "draft an answer for this application question".
- **Voice mock interview:** pick a job, and an AI interviewer asks questions based on its description and your CV. You answer by voice and it replies by voice (ASR → LLM → TTS), with feedback at the end.
- **Profiles:** Tigran (software, AI) and his wife (business development), with different searches, keywords and CVs.

## Target architecture (short)

```
React (jobs · tracker · CV studio · assistant chat · mock interview)
   │ REST + SSE / WebSocket
   ▼
API service: FastAPI async ── Postgres + pgvector (jobs, applications, CVs, embeddings)
   │  gRPC server-streaming      │
   ▼                             │
Scraper service: async source adapters (httpx) → streams JobFound events
   │
Azure OpenAI (analysis, tools, embeddings, generation) · Azure AI Speech (interview)
Langfuse + Azure Monitor (traces, metrics, evals)
```

Details: `docs/architecture.md`.

## Milestones

Each ends in something demoable, merged by PR. **Maps to** shows which line of the job description it rehearses.

### M0: Foundations
- Backend repo layout from `CLAUDE.md`; `uv` backend. (The frontend is scaffolded in its own repo, see M1.)
- FastAPI app with `/health`; `pydantic-settings`; `.env.example`.
- ruff, mypy, pytest and pre-commit wired up.
- docker-compose with Postgres 16 + pgvector.
- **Done when:** compose starts the DB, the API serves `/health`, and linters plus a first test pass.
- **Maps to:** Python backend, tests.

### M1: Data model, import, and the jobs UI
- Tables: `profiles`, `jobs`, `job_sources`, `applications` (status, notes, timestamps), `status_history`, `cvs` (master and tailored, JSON), `cover_letters`.
- `scripts/import_legacy.py`: imports `profile.json`, `jobs.csv` (with statuses and notes), `cv/master.json`, `cv/tailored/*.json` and `cover_letters/*.md` from `~/Documents/job-hunt`.
- REST endpoints: list and filter jobs, update status and notes, get the CV.
- **Frontend repo:** scaffold the web app (Vite + React + TS) in its own repo and connect it to this API (API base URL from env, CORS enabled here).
- React: a jobs table (search, filters by location bucket, source, AI roles, status) and a job detail page with status buttons. Feature parity with the old `jobs.html`.
- **Done when:** the imported data shows in the UI and status changes persist in Postgres.
- **Maps to:** FastAPI async, new features.

### M2: Async scraper (in-process first)
- Port the sources from `jobhunt.py` to async adapters with a shared interface (`async def fetch(profile) -> AsyncIterator[RawJob]`), using `httpx.AsyncClient`, per-source rate limits and retry/back-off.
- Normalisation, dedupe (URL plus company/title), the location rules, and keyword scoring ported as-is first.
- `POST /scrape` starts a run; progress streams to the UI over SSE ("LinkedIn: 45 found…").
- Tests with recorded fixtures per source.
- **Done when:** a run from the UI fills the DB, progress shows live, and no test touches the network.
- **Maps to:** async Python, latency/streaming basics.

### M3: The scraper as a gRPC service
- `proto/scraper.proto`: `RunScrape(ScrapeRequest) returns (stream ScrapeEvent)` server streaming with progress, job-found, source-error and done events; a `Cancel` path.
- The scraper becomes its own `grpc.aio` service; the API consumes the stream, writes to the DB and relays progress to the browser.
- Deadlines, cancellation, the gRPC health check, and an in-process gRPC server for tests.
- An ADR on why gRPC here and what it costs.
- **Done when:** the same UI flow works across two services, and cancelling from the UI stops the scrape.
- **Maps to:** gRPC streaming, service boundaries.

### M4: LLM job analysis (structured outputs + prompt engineering)
- For each new job: Azure OpenAI with **structured outputs** (a Pydantic schema) extracts `required_skills`, `nice_to_have`, `seniority`, `employment_type`, `location_eligibility` (countries or regions, Armenia ok?, relocation?), `us_hours`, `salary`, and `red_flags` (pay-to-apply, crypto-only pay, anonymous agency…).
- This replaces the regex heuristics (US hours, "Worldwide" that's really US-only); the old heuristics stay as a cheap pre-filter.
- Prompt in Langfuse prompt management; cost control by analysing only jobs that pass the pre-filter, with batching and caching by content hash.
- **Done when:** analysis is stored per job and shown on the job page, and the location filter uses it.
- **Maps to:** LLM integration, prompt engineering.

### M5: Embeddings, matching and RAG
- Embed job descriptions and every master-CV bullet (`text-embedding-3-small`) into `pgvector` (HNSW index).
- **Fit score** = keyword score + semantic similarity (job ↔ CV bullets) + analysis signals (eligibility, seniority match). Show "why it matches" with the top CV bullets.
- "Similar jobs" and semantic search ("agentic engineering roles with React").
- **Retrieval for tailoring:** pull the CV bullets most relevant to a job (this is the RAG step M6 uses).
- **Done when:** the job list can sort by fit score, and each job shows its top matching bullets.
- **Maps to:** RAG/embeddings, vector search.

### M6: Assistant with tool calling, CV tailoring and cover letters
- The **assistant chat** with tools: `search_jobs`, `get_job`, `get_master_cv`, `retrieve_cv_bullets`, `tailor_cv`, `write_cover_letter`, `update_application_status`, `draft_form_answer`. Tool-calling loop with step limits, parallel tool calls, and validation errors returned to the model.
- **Tailoring** produces a tailored CV as structured output. A **validator** checks it against the master: every bullet maps to a master bullet (exact or rephrased, checked by embedding similarity and number/name preservation), no new skills, and dates, titles, companies and numbers unchanged. Violations are rejected and regenerated.
- **Cover letters** stream token by token to the UI; editable and saved per job.
- PDF rendering ported from `cv/build_cv.py`.
- **Done when:** "tailor my CV and write a letter for job X" works end to end from the chat, and the validator catches an injected fake skill in a test.
- **Maps to:** tool calling, prompt engineering, new use cases.

### M7: Observability and evals
- Langfuse: one trace per assistant turn or scrape analysis, with tokens, cost and latency; prompts versioned.
- `evals/`: golden sets for (a) job analysis (≈40 real postings with expected eligibility, US hours and red flags, including the cases from the old tool: Wrapbook "Worldwide" but US-only, Pavago US hours, Saifuro flagged), and (b) tailoring honesty (letters and CVs must not invent anything; an LLM-as-judge with a rubric plus the deterministic validator).
- OpenTelemetry → Azure Monitor: request latency, scrape duration per source, LLM latency.
- **Done when:** one command prints an eval table, and a prompt change visibly moves the scores.
- **Maps to:** Langfuse, monitoring, measuring quality.

### M8: Voice mock interview (ASR → LLM → TTS)
- Pick a job → the interviewer persona is built from its description and analysis plus your CV.
- Browser mic (AudioWorklet, 16 kHz PCM) → WebSocket → API → Azure AI Speech **streaming ASR** → LLM interviewer (streaming) → **sentence chunker** → Azure **TTS** streaming → audio back to the browser. Barge-in cancels playback and generation.
- Optionally a separate `interview` gRPC bidi-streaming service (reusing the M3 patterns).
- A latency panel: end of speech → transcript → first token → first audio. Optimise time to first audio.
- Feedback at the end: strengths, weak answers, and what to prepare, saved to the job's notes.
- **Done when:** a spoken mock interview works with first audio well under the full answer time, and latency per stage is visible and traced.
- **Maps to:** voice assistant use cases, the ASR → LLM → TTS chain, latency.

### M9: Containers, Azure DevOps and Azure deployment
- Multi-stage Dockerfiles (api, scraper, frontend via nginx; Chromium for PDFs in the api image); non-root users.
- docker-compose runs the full app locally, with optional self-hosted Langfuse.
- Azure DevOps YAML pipelines: lint → type-check → tests → build → push to ACR → deploy to **Azure Container Apps**, with secrets from a variable group or Key Vault. Scheduled scrape via a Container Apps job (daily).
- Application Insights dashboard plus one alert (e.g. a scrape failing or LLM error rate).
- **Done when:** a merge to `main` deploys, the scrape runs daily in Azure, and the dashboard shows it. Monthly cost written down, with a teardown script.
- **Maps to:** containerised services, Azure DevOps pipelines, Azure Monitor.

### M10 (stretch, the "senior" items)
- **Multi-LLM:** a second provider behind the interface, plus a router (a cheap, fast model for job analysis and a strong one for letters and tailoring, with fallback on errors). Compare cost, latency and eval scores.
- **Kubernetes:** a Helm chart or manifests for AKS (or kind locally); an ADR on Container Apps vs AKS.
- **Inbox sync:** connect Gmail read-only, classify application emails (confirmation, rejection, next step, red flag) with the LLM, and update the tracker automatically, with human confirmation.
- **Load test** of the API with k6 or Locust.
- **Maps to:** architecture input (multi-LLM, Kubernetes), technical ownership.

## Accounts and costs

- **Azure:** set a **budget alert** on day one. Azure OpenAI and Speech are pay-as-you-go (Speech has a free tier); Container Apps has a monthly free allowance; the smallest Postgres Flexible Server tier, or keep Postgres in a container for dev.
- **Langfuse:** a cloud free tier, or self-hosted.
- **Azure DevOps:** free tier for small projects; check the current pipeline-minute terms.
- **Cost guardrails in code:** analyse only pre-filtered jobs, cache by content hash, embed once per job, and set daily token budgets per feature.

## What to show in interviews

- A 2–3 minute demo: a live scrape streaming in → a job with LLM analysis and fit explanation → "tailor CV + letter" from the chat → PDF → a short voice mock interview with the latency panel.
- The eval table (job-analysis accuracy, tailoring-honesty pass rate) before and after a prompt change.
- The tailoring validator: "how I stopped the LLM from inventing experience."
- ADRs: gRPC for the scraper, structured outputs vs regex, pgvector, Container Apps vs AKS, the multi-LLM routing policy.
